# superlive Roadmap and Module Process

> This is the authoritative document for the long-haul task: module sequence, hard process rules, layout conventions. Owner acceptance and expert review both take this file and [architecture.md](architecture.md) as the baseline.

## Hard process rules (every module walks the full chain, no step may be skipped)

```
development done → expert review (against the authoritative docs) → fix per review findings → code cleanup → expert acceptance → only then open the next module
```

- Expert review and acceptance are benchmarked against the authoritative documents under docs/; a discrepancy between docs and discussion is treated as an incident
- Code cleanup means the convergence checklist (dead code/imports/comment sync/compile & type check/lint/full test suite)
- No new module opens until the previous one passes expert acceptance
- **Mandatory action after each module (owner contract)**: cross-check this document and the task plan's progress records, pick the next module accordingly; **the finish condition is all modules complete — no stopping midway**

## Layout conventions

- All component projects sit at the same level as xatodo, spread under `~/Projects/drodreo/`
- Component naming: the `sl-<domain>` prefix (e.g. sl-events, sl-knowledge), distinct from the superlive repository (the platform)
- The original superlive repository stays untouched as the reference source for the splits — no in-place rework

## Autonomous progress discipline (while the owner is asleep)

- Keep pushing, do not wait for confirmation; on decisions, act autonomously per the authoritative documents and the spirit of the discussions, and record the decision and reasoning in the diary/this file for the owner's audit on waking
- Documents always come first: when implementation and documents conflict, fix one of them to keep both aligned
- git commits by logical unit, Chinese commit messages

## Module 5 design decisions (sl-events, ruled after the survey of 2026-09-20)

Survey findings (full report in that day's conversation): the events domain's core side is 8 files with high self-containment (~1450 lines); the only two cross-domain dependencies are the entity existence check on add (entries::get_active) and the delete cascade over entry_tags (the tag facility belongs to the knowledge domain); the UI side's dedicated files move wholesale but depend on the CrudListPage shared facilities; the overview tab (FullCalendar+Timeline) currently idles as an unconnected demo; article_workflow_events has zero dependency on this domain (a naming coincidence, writing domain).

Eight rulings (self-made decisions recorded for audit; the owner may overturn on waking):
1. **v1 scope**: full CRUD on the list tab (CrudListPage shape); the overview tab is not carried (demo idle code is not worth migrating; FullCalendar/Timeline stay in superlive); Timeline.tsx has a second consumer (articles also uses it) and does not move
2. **server structure**: single crate (the skeleton is settled; a single-table domain needs no xatodo-style three-crate workspace) — dual-mode main + component assembly (reusing the xatodo pattern) + entity (events table + migration) + dgpqp copy (7 files lifted from superlive core/src/dgpqp, the query-translation common facilities) + service + routes
3. **entity strict check → weak reference**: add no longer checks entries::get_active (cross-component data is unreachable; the original system never cascaded events on entry deletion — weak consistency is the pre-existing fact) — revisit cross-component validation after module 6 splits out the knowledge domain
4. **entry_tags cascade + tag association not carried**: the tag facility belongs to the knowledge domain and is module 6's input; delete only soft-deletes itself
5. **dead code not carried**: the dead category='entity' condition (EventResolver silently skips unmapped) and the dead embeddingStatus field (no such table column) are cleaned, not implemented as dead semantics
6. **CLI dropped**: the component form has no CLI; commands/event.rs's clap wiring does not migrate (functionality equals HTTP)
7. **legacy data not migrated**: the new database starts empty; the superlive monolith keeps holding the old data. A migration plan awaits the owner's word
8. **CrudListPage facilities copied into the component** (not a shared package): lift the minimal facility set from superlive ui (CrudListPage/QueryListToolbar/FormField/schema mechanism/dgpqp frontend types) as the component's private UI; a shared UI package (@shell/ui-common or similar) is deferred — decide when the copy-drift pain across components actually appears; demand-driven, no speculative design

Component identity: id=sl-events, namespace=events, display_name=dynamic tracking, ui_type=module. The API contract keeps its original shape (POST /api/events/search, batch POST/PUT/DELETE, GET {id}, BatchResult/SearchResponse defined locally). The component-form config has only database_url (no users/apikey, simpler than xatodo). Packaging reuses the xatodo three-script pattern.

## Module 9 design decisions (sl-finance, ruled after the survey of 2026-09-21)

Survey core facts: the finance domain = the markets/stock_ticks/regions tables + the stock_analyze single endpoint + the tushare external integration (sync pipeline + cron). **The heaviest cross-domain dependency since modules 5-8**: four dependencies on the knowledge domain's entries (the sync placeholder write / the markets add check / the analyze name lookup / the UI selector), of which sync's ensure_entity is a cross-domain write. Reverse cascades are zero (entries::delete never touches the finance tables; orphan tolerance is consistent with "a tick is a fact"). Scale is third-heaviest of the nine modules; external-integration complexity is the highest (the only external API + cron + token configuration).

1. **entries dependency = an in-domain self-owned mapping** (heaviest ruling, self-made for audit, the owner may overturn on waking): a new minimal in-domain entity mapping table (ts_code↔internal id; sync auto-registers, carrying over the original's "tushare placeholder entity" automation semantics); the markets add check / the stock_analyze lookup now query the in-domain mapping; the cross-component API option was rejected (it would violate the "components do not know each other" architecture decision); "the sl-knowledge graph cannot see stocks" is an inevitability of componentization, not a cost unique to this plan
2. **tushare integration migrated wholesale**: tushare-api + token + rate-limit retry (120 per 1200ms + 3 exponential backoffs) moved verbatim; token/schedule move from the superlive Config into the component's own config ([tushare] section: token + schedule)
3. **sync triggers**: cron (tokio-cron-scheduler) owned by the component process (spawned inside slsdk serve); **new POST /api/tushare/sync manual endpoint** (after the CLI's retirement, HTTP is the only manual channel in the component environment — the original's lack of this endpoint is a CLI-era artifact)
4. **stock_ticks 501 trio as-is** (PUT/DELETE/GET return 501 directly, the v7 "ticks are factual data" decision); the batch side's 3 allow(dead_code) stub functions are not carried
5. **regions goes with the domain**; the markets.region string's zero association with the regions table is preserved (original semantics first)
6. **Hardcoded demo not carried** (the stocks overview's indices/sectors/markets chart tabs — the "only clean when the boss gives a clear signal before commit" comment marks it undecided; not carrying it into the component is the clean choice); the speedview real functionality is kept
7. **ECharts on-demand register** (candlestick+line+grid+tooltip components, to control bundle size; the full import was rejected)
